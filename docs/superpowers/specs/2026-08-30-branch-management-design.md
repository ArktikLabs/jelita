# Branch Management — Design

**Status:** Approved design, not yet implemented
**Date:** 30 August 2026
**Context:** Jelita / Arktik Salon Suite (see `docs/prd-salon-management-mvp.md`)

---

## 1. Context

Tenancy is built and tested: organization = salon = billable tenant, team =
branch. Plan gating enforces a per-tier branch cap and computes read-only locks
for branches over that cap. The app has a shell, page guards, Server Action
form patterns and shadcn/ui.

What a branch does not have is any data. `teams` carries `name`,
`member_count`, `organization_id` and timestamps — nothing else. There is no
screen for creating, editing or switching branches, and `activeTeamId` has
exactly one consumer (`requireBranch()`), so nothing surfaces it to a user.

This design gives a branch a real record, and gives an owner the screens to
manage one.

## 2. Goals

- A branch carries name, contact, location and per-weekday opening hours
  including days off.
- Owners and admins can create, edit, deactivate and reactivate branches, and
  switch which one they are working in.
- Front desk and stylists see which branch they are in and cannot change it
  (PRD §5.8).
- Closing a branch preserves its history and stops operations, without
  changing what the salon is billed for.

## 3. Non-goals

- No per-branch timezone. See §4.
- No consolidated cross-branch dashboard or inter-branch transfer (PRD §5.8
  defers both).
- No hard deletion of branches.
- No map coordinates or geocoding; address is free text.
- No staff management screens — that is the next piece of work.

## 4. Decisions

| Question | Decision | Rationale |
|---|---|---|
| Branch data | name, contact, location, per-day hours, day off | Hours feed §5.1 availability directly |
| Closing a branch | Deactivate; still counts toward creation, but holds no lock slot | Billing is unchanged; a live branch is never locked by a closed one |
| Staff on a closed branch | Deactivation is **blocked** until they are reassigned | Surfaces the problem to the person who can fix it |
| Timezone | **None.** Hours are plain times read as `Asia/Jakarta` | See below |
| Where branch data lives | New tables keyed to `teams.id` | `lib/schema/auth.ts` is regenerated by the better-auth CLI |

**On timezone.** Indonesia spans three zones, so a chain could in principle
straddle them. It was deliberately left out: a customer books the branch
nearest them, so no conversion arises in the booking flow; booking instants are
stored as `timestamptz` and are unambiguous regardless; and only opening hours
are wall-clock, which is per-branch config that is cheap to reinterpret. If a
cross-zone chain ever signs up, existing rows backfill correctly to
`Asia/Jakarta` because that is genuinely what they were. The one real case is
an admin reading another zone's calendar, which would be noticed immediately
rather than corrupting data silently.

## 5. Data model

```sql
create table branch_profiles (
  team_id text primary key references teams(id) on delete cascade,
  address text,
  phone text,
  active boolean not null default true,
  deactivated_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table branch_hours (
  team_id text not null references teams(id) on delete cascade,
  weekday smallint not null check (weekday between 0 and 6),
  closed boolean not null default false,
  opens_at time not null default '09:00',
  closes_at time not null default '21:00',
  primary key (team_id, weekday),
  check (closed or closes_at > opens_at)
);
```

`weekday` uses **0 = Sunday**, matching Postgres `extract(dow)`, so the
availability engine joins on it without an off-by-one translation layer. The
check constraint lets a closed day hold meaningless times while forcing an open
day to hold sane ones.

**Rows are created by an `after insert on teams` trigger, not by application
code.** better-auth creates teams this codebase never sees — the organization
plugin auto-creates a default team during signup. The trigger writes the
profile row and seven `branch_hours` rows so a branch created by any path is
always fully configured.

Defaults are every day 09:00–21:00, none closed — deliberately
over-permissive. An owner narrowing hours is routine; a branch that silently
accepts no bookings looks broken.

**Why not absence-means-closed.** Omitting a row for a day off would match the
`plan_limits` convention, but it makes a newly created branch closed every day
until someone configures it. Seven seeded rows plus an explicit `closed` flag
means "not configured" never exists as a state.

`teams.created_at` is `timestamp without time zone` in better-auth's generated
schema while these tables use `timestamptz`. Accepted rather than hand-editing
generated code.

## 6. Changes to shipped plan-gating code

A deactivated branch still counts toward the branch cap, so `countResource`
needs no change — it already counts every team. But the **lock ranking** is a
separate mechanism, and leaving it alone causes a trap.

**The trap.** Cap 1, at a salon that closed its original location and kept the
newer one: branch A (older, deactivated) and branch B (active).
`branch_entitlement` ranks all teams by `created_at`, so A gets `seq 1` and B
gets `seq 2`. With cap 1, A keeps the slot and **B — the only open branch —
goes read-only.** The owner has one branch, pays for one branch, and cannot use
it, while the closed one holds the slot.

Ranking only active branches fixes it without touching the count: B becomes
`seq 1` and stays operable, while creating a third is still blocked because the
count is 2. Both halves hold.

So, in one new migration (`0004` is applied and must not be edited):

- `branch_entitlement`'s `ranked` CTE filters to active branches **before**
  `row_number()`.
- Its `is_active` column is renamed **`within_cap`**. `branch_profiles.active`
  means "not deactivated" and the view's column means "within the tier's cap" —
  two different concepts sharing one word in queries that join them. One
  consumer today, so the rename is cheap now and permanently confusing later.

And in application code:

- `isBranchActive(teamId): Promise<boolean>` becomes
  `getBranchStatus(teamId): Promise<'ok' | 'over_cap' | 'closed'>`.
- `requireBranch({ write: true })` maps `over_cap` to
  `PlanError('BRANCH_LOCKED')` → **402**, and `closed` to
  `Error('BRANCH_CLOSED')` → **409**.
- The session-create hook in `lib/auth.ts` prefers the oldest **active** branch.
  A closed branch is a legitimate place to stand for reading history, but it is
  a poor place to land on a fresh login.

`countResource('branches')` is deliberately **unchanged**: deactivation does not
give a slot back.

**Why two error codes.** Both states are read-only, for opposite reasons.
Over-cap is a tier problem whose remedy is "upgrade"; deactivated is a decision
the owner made, whose remedy is "reactivate". Showing an upgrade prompt to
someone who closed their own branch is the same class of mistake as conflating
403 with 402.

## 7. The selector and scoping

Owner and admin get a switcher; front desk and stylists get a static label.
This maps onto `branch: ['switch']`, which only owner and admin hold.

The switch is a Server Action calling `auth.api.setActiveTeam` that
**re-checks the permission server-side**. Conditional rendering is
presentation; the action is a public POST endpoint and guards itself.

**To verify at implementation:** whether better-auth's `setActiveTeam`
validates that the target team belongs to the caller's organization. If it does
not, this codebase adds that check. Not assumed — the cross-tenant defect found
in the auth work came from exactly this kind of unverified assumption.

| Branch state | In selector | Behaviour |
|---|---|---|
| Active, within cap | yes | fully operable |
| Active, over cap | yes, marked *Terkunci — upgrade* | selectable, read-only |
| Deactivated | yes, marked *Nonaktif* | selectable, read-only |

Keeping closed branches in the switcher means an admin can still stand in one
to read its history, so §5.6 reports are free to filter by branch without also
having to carry that job.

It also removes a piece of machinery: because a closed branch is a legitimate
place to be, there is no need to detect "your active branch was deactivated
underneath you" and move the user somewhere else. The branch simply gains its
label and goes read-only.

**One state is still prevented rather than handled:** the last active branch
cannot be deactivated. An admin left with nothing but closed branches can read
history and change nothing, which is a support call rather than a workflow.

## 8. Screens

| Route | Guard | Contents |
|---|---|---|
| `/branches` | `branch: ['update']` | list: name, address, phone, status, staff count |
| `/branches/new` | `branch: ['create']` + `requireQuota('branches')` | name, address, phone |
| `/branches/[id]` | `branch: ['update']` | details, hours, deactivate / reactivate |

Routes rather than dialogs, matching the auth screens: Server Actions work
naturally, forms degrade without JS, each branch is deep-linkable.

**A sixth change to shipped code, needed by these guards.** `lib/session.ts`
has `requirePageSession` and `requirePageOrg`, which redirect, and
`requirePermission`, which throws. There is no redirecting permission guard, so
a front-desk user hitting `/branches` would hit an error boundary rather than
being sent somewhere sensible. Add `requirePagePermission(perms)` alongside the
other page guards: same permission check as `requirePermission`, but
`redirect('/dashboard')` on failure instead of throwing. The throwing version
stays untouched — API routes still need their status code.

**The list is guarded on `update`, not `read`.** Everyone holds `branch:
['read']` — that is what lets a stylist see which branch they are in — but a
screen carrying edit and deactivate controls should not render for front desk.
Status is a badge per row: *Aktif*, *Terkunci*, or *Nonaktif*.

**Create collects name, address and phone only.** Hours arrive pre-seeded and
are edited on the detail page; 21 time inputs in a creation form is how people
abandon it. Creation calls `auth.api.createTeam`, which already fires the
`beforeCreateTeam` quota hook, so the action's job is catching that `402` and
rendering an upgrade message.

**The detail page carries three independent Server Actions** — details, hours,
and deactivate/reactivate — so one failure does not discard the others' input.
The deactivate action enforces both blocking rules and says *which* applies,
naming the staff still assigned or refusing as the last active branch.

**New shadcn components:** `table`, `badge`, `checkbox`, `select`.

**Accepted trade-off.** shadcn's `select` is a client component, so the
switcher will not work without JS — unlike the auth forms, where progressive
enhancement was a stated reason for Server Actions. Acceptable because
switching branches is an admin convenience rather than a critical path, and a
native `<select>` would be noticeably worse in the control this app uses most.

## 9. Testing

**New suite — `scripts/branch-check.mjs`**, assert-and-count style with an
unconditional section-0 reset, matching the three existing suites:

1. Creating a team creates one profile row and exactly seven hours rows
2. Deactivation is refused while staff are assigned, and the error names them
3. Deactivation is refused when it is the last active branch
4. Deactivating does **not** free a slot: at cap, deactivate a branch, and
   creating another still returns 402
5. **Cap 1 with the oldest branch deactivated — the remaining active branch
   stays operable**
6. `getBranchStatus` returns `closed` for deactivated, `over_cap` for over-cap,
   `ok` otherwise
7. A fresh login lands on an active branch, never a deactivated one
8. `/branches` refuses a front-desk user
9. The switch action rejects a team belonging to another organization
10. A deactivated branch still appears in the switcher, is selectable, and
    refuses writes with `BRANCH_CLOSED` rather than `BRANCH_LOCKED`

Assertion 5 is the regression test for §6's bug. **It must be shown to fail**
when the inactive filter is removed from the view's `ranked` CTE — an assertion
that cannot fail reads as coverage without being it.

Assertion 9's implementation depends on what `setActiveTeam` already
validates; the assertion is the same either way.

## 10. Forced changes to existing work

- `countResource('branches')` is NOT changed. Deactivation affects locking, not
  billing.
- `scripts/plan-check.mjs` reads `is_active` from `branch_entitlement` in its
  section-4 lock assertions and calls `isBranchActive` directly in section 10.
  Both break under §6. These are **rewrites, not deletions** — the count stays
  at **38**. A different number means an assertion was lost.
- `lib/session.ts` gains `requirePagePermission` (see §8). `requirePermission`
  is not modified — both are needed, for the same reason both
  `requireUser`/`requirePageSession` are.
- Existing suites stay green: auth **70**, plan **38**, ui **16**.

## 11. Deferred, with the trigger for revisiting

- **Per-branch timezone.** Revisit when a chain operates across WIB/WITA/WIT.
- **Hard deletion.** Revisit if branches created by mistake become a real
  support burden.
- **Map coordinates.** Revisit if the public booking page wants a map pin.
