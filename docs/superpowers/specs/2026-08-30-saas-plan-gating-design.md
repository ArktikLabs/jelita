# SaaS Plan Gating — Design

**Status:** Approved design, not yet implemented
**Date:** 30 August 2026
**Context:** Jelita / Arktik Salon Suite (see `docs/prd-salon-management-mvp.md`)

---

## 1. Context

The salon product is multi-tenant: `organization` = salon (the billable
tenant), `team` = branch. An authorization layer already exists and is tested
— roles (`owner`, `admin`, `frontdesk`, `stylist`), per-tenant runtime custom
roles, and `requirePermission()`.

This design adds the layer **above** it: Arktik decides what a given salon is
allowed to have at all. The owner then distributes that allowance to staff
using the existing role system.

The two layers are deliberately separate mechanisms. A plan limit is not a
permission: an owner always *has* `branch:create`, but their tier may have no
room. The correct response is "upgrade", not "access denied" — different
error, different screen, different code path.

## 2. Goals

- Arktik defines tiers as **data**: feature set, resource caps, and price.
- Limits are **enforced server-side**, not merely displayed.
- **Payment-ready**, not payment-integrated: the model holds price, status,
  and billing period so a gateway plugs in later (same adapter posture as
  PRD §5.10).
- Tier data is seeded now and written by a **separate internal Arktik app**
  later. The salon app only ever reads it.

## 3. Non-goals

- No payment gateway, subscription lifecycle, proration, or dunning.
- No Arktik-facing console in this codebase. No platform-admin auth surface,
  and therefore **no better-auth `admin` plugin** (its roles are global; see
  §11).
- No usage-based metering (bookings/month, SMS counts). Caps are on countable
  resources only.

## 4. Decisions

| Question | Decision | Rationale |
|---|---|---|
| Scope | Enforced limits, no payments; prepare for them | Demoable and real, without a gateway on the critical path |
| Tier authoring | Seeded rows; separate internal app later | Salon app is read-only w.r.t. tiers; no admin surface to secure |
| Over cap | Block new **and** lock the excess | Tier stays truthful; no data destroyed |
| Which survive | Oldest N by creation; owner cannot override | Deterministic, so lock state needs no storage |
| Locked means | Read-only, still fully visible | Commercial pressure without looking like data loss |

## 5. Data model

Normalized (chosen over a JSONB entitlements blob). `organizations` and
`teams` belong to better-auth and are regenerated by its CLI, so nothing may
be added to them — the subscription must be its own table regardless.

```sql
create table features (
  key text primary key check (key ~ '^[a-z_]+$'),
  label text not null,
  description text,
  sort_order int not null default 0
);

create table plans (
  id bigint generated always as identity primary key,
  key text not null unique check (key ~ '^[a-z_]+$'),
  name text not null,
  price_idr bigint not null default 0 check (price_idr >= 0),
  billing_interval text not null default 'month'
    check (billing_interval in ('month','year')),
  is_default boolean not null default false,
  active boolean not null default true,
  sort_order int not null default 0
);
create unique index plans_one_default on plans (is_default) where is_default;

create table plan_limits (
  plan_id bigint not null references plans(id) on delete cascade,
  resource text not null
    check (resource in ('branches','staff','services','products')),
  cap int not null check (cap >= 0),
  primary key (plan_id, resource)
);

create table plan_features (
  plan_id bigint not null references plans(id) on delete cascade,
  feature_key text not null references features(key) on delete restrict,
  primary key (plan_id, feature_key)
);
create index plan_features_feature_idx on plan_features (feature_key);

create table subscriptions (
  id bigint generated always as identity primary key,
  organization_id text not null unique
    references organizations(id) on delete cascade,
  plan_id bigint not null references plans(id),
  status text not null default 'active'
    check (status in ('trialing','active','past_due','canceled')),
  current_period_start timestamptz not null default now(),
  current_period_end timestamptz,
  provider text not null default 'manual',
  provider_ref text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create index subscriptions_plan_idx on subscriptions (plan_id);
```

Conventions:

- **Unlimited = absence of a `plan_limits` row.** No sentinel values.
- **`features` is a table, `resource` is a CHECK.** Features need `label` and
  `description` for the pricing page and future console, so the row earns its
  place beyond integrity. Resources are a fixed set hard-coded into
  enforcement logic; a catalog table you cannot extend without shipping code
  is ceremony.
- **One subscription per tenant** (`unique organization_id`). Entitlement
  resolution is a single-row lookup. Billing history, when it arrives, is a
  separate `subscription_events` table rather than multiple subscription rows.
- **`plans_one_default`** guarantees at DB level that a new tenant can never
  land with no entitlements.

## 6. Entitlement resolution

Storage is normalized; the read is not. One query returns caps as a JSON
object and features as an array, so no guard joins at call time:

```sql
select p.key as plan_key, p.name as plan_name, s.status,
       (select coalesce(json_object_agg(l.resource, l.cap), '{}')
          from plan_limits l where l.plan_id = p.id) as caps,
       (select coalesce(json_agg(f.feature_key), '[]')
          from plan_features f where f.plan_id = p.id) as features
  from subscriptions s
  join plans p on p.id = s.plan_id
 where s.organization_id = $1;
```

Exposed as `getEntitlements(organizationId)` in `lib/entitlements.ts`,
memoised with React `cache()` so a page calling several guards issues one
query per request.

### Every tenant always has a subscription

An `after insert on organizations` trigger creates a subscription on the plan
flagged `is_default`.

A database trigger is chosen over better-auth's
`organizationCreation.afterCreate` hook because a separate internal Arktik app
will create and modify organizations without passing through this codebase. A
hook covers only writers in this app; the trigger covers every writer.

Defensively, `getEntitlements` falls back to the default plan if the row is
missing — a data glitch must not 500 a salon mid-service — and the test suite
asserts every organization has a subscription, so drift fails a test run
rather than hiding.

### Status → entitlements

| Status | Resolves to |
|---|---|
| `trialing`, `active` | the subscription's plan |
| `past_due` | the subscription's plan (unchanged) |
| `canceled` | **the default plan** |

Cancellation therefore needs no dedicated code: it resolves to the free tier's
caps and the lock rule (§8) does the rest. `past_due` retaining full access is
deliberate — a failed charge must not lock a salon mid-shift. Dunning arrives
with the gateway.

## 7. Enforcement

Three guards beside the existing role guard:

```ts
await requirePermission({ pos: ['void'] })   // existing — role
await requireFeature('payroll')              // tier includes it?
await requireQuota('branches')               // room for one more?
await requireBranch({ write: true })         // existing, extended
```

### HTTP semantics

- `403 Forbidden` — the **user's role** lacks the permission. Unchanged.
- `402 Payment Required` — the **tenant's tier** is the blocker, with a
  distinct code in the body: `FEATURE_NOT_IN_PLAN`, `QUOTA_EXCEEDED`,
  `BRANCH_LOCKED`.

One status the client keys on to show an upgrade modal, codes to pick the
wording. `403` means *you* can't; `402` means *this salon* can't.

### Errors carry data

```ts
class PlanError extends Error {
  constructor(public code: PlanErrorCode, public meta: PlanErrorMeta) {
    super(code)
  }
}
// meta: { resource, cap, used, planKey, planName }
```

The UI must render "Starter includes 3 branches. You have 3." A bare message
cannot. Existing guards keep throwing plain `Error('FORBIDDEN')`; they are not
refactored as part of this work.

### Enforcement points

Some resource-creating paths are **better-auth's own endpoints** and cannot be
guarded from our route handlers. Those use a `hooks.before` middleware
(verified against better-auth 1.7.2: `createAuthMiddleware` from
`better-auth/api`, dispatching on `ctx.path`).

| Path | Consumes | Guarded by |
|---|---|---|
| `POST /organization/create-team` | a branch | `hooks.before` |
| `POST /organization/accept-invitation` | a staff seat | `hooks.before` |
| `POST /api/staff` | a staff seat | in-handler `requireQuota` |
| `POST /organization/invite-member` | no seat (pending) | `hooks.before`, courtesy check |

Seats are counted as rows in `members`; a pending invitation does **not** hold
a seat. Enforcement therefore happens at *acceptance*, the moment a seat is
actually consumed. Invite-time is also checked, but only as a UX courtesy so
an owner learns early — acceptance is the authoritative gate.

Staff count **includes the owner**, on the basis that a seat is a login.

Branch-scoped writes ride on `requireBranch()`, which every such path already
passes through. Extending that one function makes bookings, checkout, and
stock movements inherit locked-branch enforcement without per-endpoint checks
— PRD §7's "enforced at the API layer, not per-endpoint" applied to
entitlements.

## 8. Locked resources

Lock state is **computed, never stored**. Because the rule is "oldest N
survive and the owner cannot override", lockedness is a pure function of
`(cap, creation rank)`. There is no lock column, no unlock endpoint, and no
state machine to drift; raising a cap unlocks automatically.

```sql
create view effective_plan as
select o.id as organization_id,
       coalesce(
         case when s.status = 'canceled' then null else s.plan_id end,
         (select id from plans where is_default)
       ) as plan_id
  from organizations o
  left join subscriptions s on s.organization_id = o.id;

create view branch_entitlement as
with ranked as (
  select t.id, t.organization_id,
         row_number() over (partition by t.organization_id
                            order by t.created_at, t.id) as seq
    from teams t
)
select r.id as team_id, r.organization_id, r.seq, l.cap,
       (l.cap is null or r.seq <= l.cap) as is_active
  from ranked r
  join effective_plan e on e.organization_id = r.organization_id
  left join plan_limits l
    on l.plan_id = e.plan_id and l.resource = 'branches';
```

`order by created_at, id` tiebreaks deterministically; seeded rows routinely
share a timestamp, and without the tiebreak "which branch is locked" could
change between queries.

Views live in a `--custom` Drizzle migration and are queried through Drizzle's
`sql` template. They are not modelled in the schema DSL.

**Locked = read-only.** No new bookings, checkouts, or stock movements at that
branch. Everything remains viewable — past transactions, reports, customer
history — and the branch still appears in the selector, marked
"Locked — upgrade to reactivate".

**The organization's auto-created team counts as branch #1.** better-auth's
organization plugin creates a team named after the organization on creation.
It is treated as the salon's first branch, to be renamed by the owner. It is
the oldest row, so it is the one that survives every downgrade — the sane
default. Deleting it instead would leave a new tenant with zero branches and
nothing they can do.

## 9. Seed data

Prices and caps are business decisions, changeable by editing a seed row
rather than shipping code.

| | `free` (default) | `starter` | `pro` | `business` |
|---|---|---|---|---|
| Price / month | Rp 0 | Rp 199.000 | Rp 499.000 | Rp 1.499.000 |
| branches | 1 | 1 | 3 | unlimited |
| staff | 3 | 8 | 25 | unlimited |
| services | 10 | 50 | unlimited | unlimited |
| products | 20 | 200 | unlimited | unlimited |
| `online_booking` | yes | yes | yes | yes |
| `commissions` | — | yes | yes | yes |
| `whatsapp` | — | yes | yes | yes |
| `inventory` | — | — | yes | yes |
| `report_export` | — | — | yes | yes |
| `payroll` | — | — | — | yes |

`online_booking` is in every tier deliberately: it is the feature that wins
the salon over, and gating it suppresses adoption. `payroll` is the top-tier
hook — PRD §5.9 is P2 and named first-to-cut, which makes it a natural upsell
rather than table stakes.

`free` is the default plan and therefore does double duty: new tenants land
there, and canceled tenants fall back to it.

Note the interaction with §8: a `free` tenant's single branch slot is consumed
by the organization's auto-created team. They operate exactly that one branch
and cannot add a second without upgrading, which is the intended behaviour.

## 10. Testing

`scripts/plan-check.mjs`, run via `pnpm plan:check`. Separate from the auth
suite; separate concern. Same no-framework, assert-and-count style.

1. A new organization always receives a subscription on the default plan
2. A second `is_default` plan is refused by the partial unique index
3. `requireFeature` returns `402` on `free`, passes on `business`
4. `requireQuota` returns `402` at cap
5. `requireQuota` passes when no `plan_limits` row exists (unlimited)
6. Three branches on `pro`, downgraded to `free` → oldest `is_active`, rest not
7. Raising the cap re-activates with no manual unlock step
8. Writing to a locked branch → `402 BRANCH_LOCKED` via `requireBranch`
9. `canceled` resolves to default plan; `past_due` retains full entitlements
10. Deleting a feature still sold by a plan is refused (`on delete restrict`)
11. The TypeScript feature catalog and the `features` table match exactly,
    in both directions

Test 11 exists specifically because the model is normalized. The FK prevents a
bad key entering `plan_features`, but nothing prevents `requireFeature('payrol')`
in application code, which would silently deny forever. Asserting that the
union and the table agree closes the gap the FK cannot reach.

Test 6 must create the three branches with distinct `created_at` values, or
assert against the `(created_at, id)` ordering, so it does not pass by
accident on timestamp collision.

## 11. Sequencing

**The business schema ships first; this ships second.** Plan gating is
Arktik-facing and demonstrates nothing to Ovarya, whereas booking and POS are
the P0 that carries the pitch. Entitlements are purely additive — new tables,
two views, guards at existing chokepoints — so nothing in the business schema
changes because they arrive later.

**One exception, to be done now regardless:** extend `requireBranch()` to
accept `{ write: true }`, backed by a stub that always allows. Every write path
built during the business schema then already routes through the correct
function, and switching the stub to real enforcement becomes a one-commit
change. PRD §9 warns that retrofitting a chokepoint costs 2–3 days; this
insurance costs roughly ten lines.

`branches` and `staff` caps are enforceable as soon as this lands. `services`
and `products` caps can be seeded immediately but stay inert until those
tables exist — they must not be presented as enforced before then.

## 12. Deferred, with the trigger for revisiting

- **Platform console + better-auth `admin` plugin.** Its roles are global,
  so granting a salon owner `admin` would expose every tenant. Correct for an
  Arktik-only operator app; revisit when that separate app is built.
- **Billing.** `subscription_events`, gateway adapter, webhooks, dunning,
  proration. Revisit when payments are actually taken.
- **Usage-based metering.** Revisit if a tier ever sells bookings/month.
- **Per-tenant cap overrides** (a negotiated "Pro but 10 branches"). Would be
  an `organization_limit_overrides` table consulted ahead of `plan_limits`.
  Revisit at the first bespoke contract.
