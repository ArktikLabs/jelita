# Reports & Analytics — Implementation Plan

**Spec:** `docs/superpowers/specs/2026-09-03-reports-design.md`
**Date:** 2026-09-03
**Shape:** read-only. No migration, no new table, no write path.

Five steps. Each ends green — full Vitest, `tsc`, and Playwright where the step
touches a screen — with break-and-restore evidence for anything load-bearing.

---

## Step 1 — `lib/reports.ts`, and its assertions

The whole slice's risk lives here. Six functions, one date range each:

Every function takes `staffUserId?: string | null` — spec §2.1's scoping is one
filter, not a second query set.

| Function | Reads | The trap |
|---|---|---|
| `revenueRange` | `transactions` | none for the branch; **scoped revenue must come from LINES**, since a transaction's total is not any one stylist's |
| `revenueByDay` | `transactions` / lines | days with no sales must appear as zero, not be missing, or the trend lies about its own shape |
| `topServices` | `transaction_lines` | **volume must be signed by `reverses_id`** (spec §2.3) |
| `staffPerformance` | `transaction_lines` + `commissions` | a product line has no `staff_user_id` and must not become a row |
| `bookingFunnel` | `bookings` | by `starts_at`; 0 rather than a division by zero on an empty range |
| `lowStock` | exists already in `lib/inventory.ts` — reuse, do not re-query |

⚠️ The scoped-revenue split is a real trap: unscoped revenue is
`sum(transactions.total)` (which includes retail and order-level discounts),
but a stylist's revenue can only be `sum(line net)` over their lines. The two
will not match for the same range, and that is correct — say so in the code
rather than letting someone "fix" it later.

Assertions: spec §5 items 1–7. The one to write first is **3**, because the
obvious query is wrong and a passing test on unvoided data proves nothing.

**Break evidence:** drop the `reverses_id` sign from volume; drop the range
bound from revenue; count the funnel by `created_at` instead of `starts_at`;
make `revenueByDay` skip empty days.

**Cross-check, not a second implementation:** §5 item 5 asserts
`staffPerformance`'s commission column equals `commissionRecap` for the same
window. Two queries over the same rows that disagree is the failure mode this
slice can most easily hide.

## Step 2 — the charts and the owner dashboard

`pnpm add recharts` (3.10, React 19 in peers). Forms and colours are settled in
spec §2.5 — single-series, one sequential hue, no legends, direct value labels
on bars. Chart components are client; the page around them stays server.

`app/dashboard/(shell)/page.tsx` becomes the role-dependent page of spec §2.1.

- Range picker: `?from=&to=`, with today/week/month preset links.
- Revenue KPI tiles, then the trend line.
- Top services (two tables, revenue and volume), staff performance, the funnel.
- Low stock, linking to `/dashboard/products`; staff performance linking to
  `/dashboard/commissions` — Flow C's later steps already have screens.

**No guard on the page.** The reports section is wrapped in a
`report:['read']` check; the page itself must stay reachable by every role.

**Break evidence:** guard the whole page instead of the section, and watch the
stylist assertion fail.

## Step 3 — the scoped view

The same sections with `staffUserId` set, for anyone holding
`commission:['read:own']` but not `report:['read']`.

Absent rather than scoped: the salon revenue tile (their own replaces it) and
low stock.

**Break evidence:** pass `null` instead of the viewer's id and watch a
stylist's figures become the branch's. This needs a SECOND stylist with sales
in the fixture — with one stylist, scoped and unscoped are identical and the
break proves nothing. (Two earlier assertions in this project failed exactly
that way.)

## Step 4 — CSV export

`app/api/reports/csv/route.ts`, guarded by `report:['export']`.

One section per request, `Content-Disposition` with a filename carrying the
range. Quoting per spec §2.6 — a helper with its own unit test, because the
seeded Indonesian service names contain commas and a broken quote is a
silently wrong spreadsheet rather than an error.

**Break evidence:** remove the quoting and assert on a comma-bearing name;
guard with `report:['read']` instead of `['export']`.

⚠️ Expect that second break to fail nothing: owner and admin hold both. If it
does, pin the overlap in `tests/permissions.test.ts` the way the payroll and
base-salary guards are pinned, rather than leaving an unfalsifiable guard.

## Step 5 — verify against the seed, then merge

`pnpm seed:demo` writes three weeks of real sales. Read the dashboard against
it and check the figures are *plausible*, not just non-zero: 186 sales, revenue
around Rp 33.7M, a no-show rate near 5%, Saturdays taller than Sundays in the
trend.

This is the step that catches a query that is wrong in a way no fixture would
show — a fixture has three sales, and three sales cannot reveal a bad `group
by`.

Then: full suite, `pnpm build`, merge to main.

## Known risks

**The trap in §2.3** is the whole reason this plan front-loads step 1. Every
other figure in the slice is a sum the ledger already makes safe.

**`/dashboard` is load-bearing for auth flows.** `tests/e2e/ui.spec.ts` asserts
that onboarding lands there and that a signed-in user is bounced there from
`/login`. Replacing the stub must not change what those see — the page stays
reachable without any permission.

**The e2e ports.** Stale `next-server` processes hold 3100–3103, so runs need
`E2E_PORT`. Not this slice's problem, but it will bite whoever runs it.
